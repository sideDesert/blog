# sideDesert architecture review

**Keep the portfolio and the art. Rebuild the scene composition boundary.** sideDesert should be a static publication for writing, projects, and an About page, with a desert illustration that visitors can explore. The artwork earns its place. The machinery for editing it belongs in a studio with a separate entry point and bundle.

I would keep one studio with two deliberately different tools. Landscape edits the home dunes and sun. Workshop inspects the layers of the three illustrated scenes against references. Keep the cactus as a way into the studio. Preserve saved artwork and the authored compositions. Move editor controls and reference assets behind the studio entry. This changes where editing happens and lets the public site load without the editor's state and tooling.

## Product needs from first principles

| Essential | Accidental today |
| --- | --- |
| Read and share a post by URL. Author posts in Obsidian with relative links and preview drafts locally. | A server-oriented deployment for static pages, a Markdown format contract repeated across build and runtime, and vault-path resolution in the reader. |
| Distinct desert compositions that respond to theme and color. Preserve silhouette, texture, layers, and their ordering. | Two embedded terrain implementations selected by caller flags, artwork naming conventions in the renderer, and repeated appearance state. |
| Inspect, edit, save, and exchange artwork. A hidden layer stays hidden, and isolation shows the selected layer. | Reconstructed layer catalogs, save effects in a public route, format guessing, and ids replaced while loading. |
| Audio requires a gesture. Motion needs to respect user preference and stay inexpensive. | Three Web Audio context owners, manual redraw overlap lists, and separate paths for steady and animated frames. |

Parnas's test is whether a given decision can change without callers learning its implementation. Applying that test here, moving a lamp should require editing its artwork, while changing the dither algorithm should require editing the renderer. Both currently touch multiple files. Parnas also warns against overspecifying interfaces. Keep canvas buffers, SVG paths, draw order bookkeeping, and storage encoding private to their owners. [Parnas, 1972, full-text reprint](https://www.cs.lafayette.edu/~gexia/cs301/resources/parnas.html)

## Modules and the decisions they hide

| Module | Decision it owns and hides | Contract |
| --- | --- | --- |
| Publication | Obsidian and Markdown conventions, draft eligibility, slug assignment, and asset/link resolution. | One compiled post catalog. Each post has stable identity, metadata, cover URLs and a renderable body. Build-only source locations stay private. |
| Site shell | Route layout, navigation, document metadata, canonical URLs and keyboard affordances. | Static pages consume publication records, project data and a scene. Keep content in its route until a second consumer needs it. |
| Appearance | System preference, saved override, color mode and first-paint bootstrap. | One resolved appearance consumed by CSS and JS. Keep preference separate from its resolved value. |
| Scene definitions | Composition, geometry, authored crop, layers, theme variations, hotspot semantics and animation intent. | An ordered scene with stable layer identities and typed payloads. Public and reference compositions are explicit documents where their artwork differs, sharing the layers they actually share. |
| Scene renderer | SVG/DOM/Canvas backend choice, dither sampling, palettes, raster scale, occlusion, caching and redraw scheduling. | Render a scene for an appearance and a layer selection. Specific scene ids and asset names stay inside scene definitions. |
| Studio | Selection, history or editing operations where needed, preview options, layer inspection and comparison. | Edit a home art document or inspect a scene's own layer list. Keep the document separate from session state such as selection, draw mode and import feedback. |
| Saved art | Storage keys, format versions, migrations, validation, and import/export. | One versioned home art document with stable ids. Store changes through the same codec used by export, with a sparse override model for preferences that follow defaults. |
| Audio | Context lifetime, browser activation, mixing and sound generation. | Ambient controls plus event sounds. One context, independent gains. Browser gesture handling and cleanup stay here. |
| Static build | Route enumeration, draft exclusion, hosting base and emitted paths. | One deployable directory of HTML and assets. Keep base-path knowledge in build configuration. |

### Core model

Use a scene-local ordered list of layers. Each layer has a stable id, its editor label and any group metadata, plus a tagged rendering payload for the kinds the site actually uses. A moving payload declares its envelope and takes its own typed input. Keep time and brightness distinct. Derive inspector controls from those same layers. Derive redraw regions from the envelopes and replay overlapping layers in their original order. Bounds remain authorable where computing them costs more than declaring them. Avoid a universal scene graph or a shared type for every two-coordinate value.

The editable home terrain remains parametric. Authored workshop terrain remains drawn geometry. Give both a shared coordinate system and use the renderer's geometry boundary. Keep parametric seam settings and freehand strokes as two authoring tools if both still earn their controls, then evaluate them to one internal stroke input. SVG strings and dither marks are renderer output. They should never be the format the editor or a second scene API depends on.

## Delete first

- Remove the unused `Main` wrapper and local `cn` implementation once the import check passes. The three UI primitives already use the installed `cn` package. Make `buttonVariants` private.
- Drop the starter README sections about demo pages, server functions and API routes. Keep the Obsidian workflow and document the Pages artifact.
- Remove unused exports and files after checking dynamic imports and Vite globs. Artwork data, authoring references, and plot geometry need usage checks as assets. Line count gives no reliable signal here.

## Order and release checks

1. Capture light and dark artwork in both color modes, at desktop and mobile sizes. Capture layer isolation, a beacon flash, lamp flicker, notebook page motion, and reduced motion. Keep the current renderer as the visual baseline during replacement.
2. Move appearance and persistence to their owners. Test old saves and files, stable identity across reloads, default versus custom palettes, and edits surviving a failed storage write in memory. Put authoring behind the studio entry.
3. Replace the composition and dither path scene by scene. Keep all three compositions visible through the migration. Require pixel or deliberate visual comparison, correct overlap and theme semantics, and a redraw budget measured while visible, offscreen and resumed.
4. Switch publication and hosting after proving root and subpath builds, direct post URLs, drafts absent from shipped text, working attachments/cross-links, and correct social metadata. Remove the old runtime and compatibility paths when their callers are migrated.

The review covers the current working tree, including local scene changes. It leaves application code alone. A GitHub Pages build at `/personal-website` emitted five HTML pages with the only post marked draft. Flipping that flag in the temporary copy emitted a sixth page at the post’s direct URL with its title in the HTML. The build still generated a Nitro server in both cases. Visual parity, saved-file migration and redraw measurements are acceptance criteria for the redesign.
